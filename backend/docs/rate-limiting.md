# API rate limiting rollout

The feature is disabled until RATE_LIMIT_ENABLED=true is set. Before enabling it, use the intended database connection (confirm the Neon project/branch locally; never print credentials) and run python -m alembic current, then python -m alembic upgrade head, then python -m alembic current. The new revision is b72d5c41a930. Back up production before migration. Set RATE_LIMIT_ENABLED=true in Vercel Production environment and redeploy. To roll back behavior, remove the flag or set it false and redeploy; the table can remain.

Counters use atomic database upserts, hashed client IPs (IPv6 /64), and fixed UTC windows. Login limits count all attempts, including successes, to avoid races before password verification. Shared IPs share a quota. Fixed windows may allow bursts across window boundaries. This is not a distributed botnet defense or an account-specific limit. Vercel's trusted x-vercel-forwarded-for header is used only under VERCEL; local deployments use the socket peer and must configure trusted proxy handling separately if needed. No raw passwords, tokens, emails or IP addresses are stored by the limiter. The existing authenticated daily cron prunes expired rows. Database failure returns 503 while enabled. General API requests each incur a counter write; monitor DB load and tune quotas or add edge limiting for high traffic.

Run python -m pytest tests/test_rate_limit.py -v and the full suite. Unit tests use SQLite, not the production database. Verify PostgreSQL behavior in staging and verify HTTP 429, Retry-After and normal login/checkout from a test deployment before enabling production. Do not deliberately flood the live service. Monitor legitimate users sharing networks and tune limits if necessary.
